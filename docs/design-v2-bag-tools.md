## v2.1 钓鱼（已实现）

按原设计落地，有三处调整：

| 设计稿 | 实际实现 | 原因 |
| --- | --- | --- |
| 收线打 `reel` | 收线打**鱼名**（`carp` / `sturgeon` / `koi`） | 鱼名长短天然对应稀有度，一份数据两用 |
| 咬钩窗口 1.2 秒固定 | 铜 1.2s / 银 1.45s / 金 1.7s / 秘银 1.95s | 让钓竿升级有可感知的手感变化 |

等待咬钩期间玩家不能移动，`Esc` 可以收竿。抛竿太早不惩罚，只提示。

## v2.2 词库分层（已实现）

用户反馈两点：词不必与内容相关；后续要能换词库；按价值估词长的方向可行。

于是把「打什么词」抽成独立一层 `words.ts`：

| 原则 | 实现 |
| --- | --- |
| 词义与玩法解耦 | 动作只传「类别 + 难度档」，不传词 |
| 长度即难度即价值 | `bandForValue(价值)` → 7 个长度档（3~14 字母） |
| 自定义归入自动分档 | 按词的实际长度归入档位，用户不用手工分级 |
| 自定义优先 | 某分类一旦启用自定义词库，内置词不再掺入 |

**被推翻的旧设计**：v2.1 用鱼名当收线词，稀有度被词义绑死，换词库时会全乱。现改为按鱼价取难度档。

## v2.3 词库打磨（已实现）

v2.2 用「字母数」当难度，审下来有三个真问题，这轮一起修：

| 问题 | 修法 |
| --- | --- |
| **长度 ≠ 难度**：`zzzz` 和 `plow` 同为 4 字母，但连按一键容易十倍 | 引入**难度分**：字母数为基础，重复字符/低多样性减分，同手连击/罕见字母加分。分档与时限都改用难度分 |
| **档位覆盖有洞且回退静默**：割草「轻松」档曾是 0，自定义小词库会悄悄压平价值曲线 | 词库界面加**档位覆盖表**（每类×每档词数，空档标红）；保存自定义词库前给**难度分布预览**；补内置词填洞 |
| **重复疲劳**：只避开上一个词，小词库来回就那几个 | 取词改**洗牌袋**（一轮内不重复）+ 最近 8 词避让 |

难度分校准：正常词 ≈ 字母数；`zzzz`=1.15、`plow`=4.5、`water`=6。时限按 `难度分/字母数` 缩放（0.5~1.4 倍），同为 4 字母的 `zzzz` 比 `plow` 少 34% 时间。

**被推翻的旧设计**：v2.2 的「长度即难度」。长度只是难度的代理，真实手感还取决于键位。

## Steam 桌面化决策（已定，接缝已留）

用户后期要上 Steam。结论：**核心栈不换，只换壳 + 留平台接缝**。

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 是否重写引擎 | 否 | Canvas 2D + 零素材 + 零网络，任何 Chromium 壳直接跑；重写 = 丢弃全部代码 |
| 目标平台 | 仅 Windows | 免 Mac 公证 / Linux WebView 差异 |
| 桌面壳 | Electron | 纯 JS、零渲染输入风险、steamworks.js 成熟；Tauri 更小但要碰 Rust |
| 时机 | 先留接缝，玩法定型再包 | 不挡动物/四季开发 |

**本轮已做**：`src/platform.ts` —— 运行时探测 + `StorageAdapter`。把 game.ts / words.ts 里 5 处 `localStorage` 全部收口。浏览器走 localStorage，桌面由 preload 注入 `__FARM_DESKTOP__.storage` 接管为文件存档。

**关键认知**：上 Steam 的真正工作量不在壳，而在 **存档文件化**（Steam 云同步的前提）+ Steamworks 接入 + 打包管线 + 商店素材。接缝现在留，就是为了以后套壳时不用翻散落的存储调用。

**同步接口取舍**：`StorageAdapter` 现为同步。存档只在睡觉/出货/购买等低频时机触发，桌面阶段可用小型同步桥；若日后要异步，改动也集中在 platform.ts + 这 5 个调用点。

## v2.4 动物系统（已实现）

用户拍板：鸡 + 牛、完整心情系统。核心命题：**动物 = 每天必做的小事**，补上「浇水 → 睡觉」之间的空档，和钓鱼互补（钓鱼考反应、动物考照料）。

| 设计点 | 实现 |
| --- | --- |
| 阵容 | 鸡 600G 产蛋 70G / 牛 2200G 产奶 160G，各限 6 只 |
| 建筑 | 地图下方鸡舍 + 牛棚 + 围栏，动物有界随机游走；棚舍实心挡路 |
| 照料动作 | 喂食 / 捡蛋 / 挤奶 / 抚摸，新增 `animal` 词库分类；挤奶是三连短词 |
| 心情 → 品质 | 心情 0~100 每 25 点一星，完美打字再 +1；喂食 +8、抚摸 +6、饿过夜 −15 |
| 产物节奏 | 喂了今天 → 明天才有产物；新买动物带一份「见面礼」引导上手 |
| 交互 | 动物是游走实体，用「面朝方向 proximity」判定，而非地块格子 |

**与既有系统的接法**：
- 产物走 `items.ts` 的 `product` kind，和作物 / 鱼一样在出货箱卖（`isSellable`/`sellPrice` 复用）。
- 照料动作复用 `TypingSession`，`Pending.kind` 扩展 `feed/collect/milk/pet` + `animalId`。
- 睡觉时 `settleAnimalsOvernight` 统一结算，和作物生长并列。
- 背包加「产物」标签；图鉴 / 帮助 / 订购箱同步补动物。

**迁移**：`normalizeState` 给旧存档补 `animals: []` 与新统计项，老存档无缝升级。

**地图调整**：把原落在畜栏区的树 / 石 / 花迁到右侧空地，杂草生成排除畜栏区（`inAnimalArea`）。

## v2.5 四季（已实现）

用户拍板：反季长得慢（×2）、每季 8 天、节日后置。核心命题：**给经营加时间维度**，把「种什么只看利润」变成「什么季节种什么」。

| 设计点 | 实现 |
| --- | --- |
| 季节结构 | 一年 32 天每季 8 天，`seasonOfDay(day)` 推导，存档只记天数 |
| 作物适季 | `CropDef.season`；春萝卜/土豆/草莓、夏番茄/玉米、秋卷心菜/南瓜、冬菠菜（新增） |
| 反季生长 | `Plot.growth` 累积 0~1，当季每晚 +1、反季 +0.5，满 1 进一阶段；跨夜保留进度 |
| 季节视觉 | `PALETTES` 四套色板，换季 `applySeason` 重绘底图；冬不开花、树冠变色 |
| 季节天气 | `rollWeather(season)`：春雨 35% / 夏 15% / 秋 20% / 冬雪 40%；`weatherWaters` 雨浇灌、雪不浇灌 |
| 提示 | HUD 季节徽章、商店适季标签、换季弹窗、反季播种提醒 |

**关键取舍**：
- 反季用「生长累积」而非改 `days`，保住既有 stage 体系，旧档 `growth` 缺省按 0 无缝迁移。
- 生长倍率按「浇水那天」的季节算，跨季最后一晚仍按旧季，行为可预期。
- 雪不浇灌是刻意的冬季小挑战，和「反季慢」叠加但不过分（冬有当季菠菜）。
- 色板只染草地 / 树 / 花，土壤 / 水 / 建筑保持 constant，避免整图失真。

**新增模块** `seasons.ts`：推导 / 天气 / 倍率 / 色板集中一处，`render.ts` 与 `game.ts` 都只读它。

## v2.6 节日（已实现）

用户拍板：加简单节日。核心命题：**给四季加期待感**，且不破坏「每天都要干活」的节奏。

| 季节 | 节日 | 效果 | 加速的是 |
| --- | --- | --- | --- |
| 春 | 🌱 播种祭 | 种子半价 | 投入 |
| 夏 | 🎆 夏日祭 | 体力消耗减半 | 劳作 |
| 秋 | 🌾 丰收祭 | 出货 +50% | 变现 |
| 冬 | ✨ 星霜祭 | 产出品质 +1 星 | 提质 |

**设计取舍**：
- **只在当天有效，不累计**。若允许「攒着等节日卖」，会诱导玩家拖着一周不玩，与「每天照料」的核心冲突。
- 四个节日各加速一个环节（投入 / 劳作 / 变现 / 提质），而不是都给钱——这样每个节日提示的是「今天该做什么」，不是「今天能刷钱」。
- 品质 +1 对钓鱼 / 作物 / 动物产物**统一生效**，封顶 5 星。

**实现接法**：`festivalEffects(day)` 返回 `{seedMult, staminaMult, sellMult, qualityBonus, festival}` 一个对象，四处消费：
- `seedPrice()` → 商店与购买（显示划线原价 + 半价标签）
- `actionCost` / `animalCost` → 体力
- `sellLines` / `sellAll` → 金额（面板同步显示加成提示）
- 收获 / 挤奶捡蛋 / 收线 → 品质

**提示链**：睡前预告明天的节日 → 当天 HUD 徽章（呼吸动画）→ 出货面板标注加成 → 节日过后睡前告知「明年再见」。

## v2.7 小镇（已实现）

用户拍板：扩建单地图走过去、打村民说的话、好感+送礼（恋爱后置）。核心命题：**补上社交维度**，对话 = 打字。

| 设计点 | 实现 |
| --- | --- |
| 地图 | `MAP_W` 30→50，农场在左小镇在右，y7-8 道路相连；`TOWN_BUILDINGS` 实心、`TOWN_OPEN` 村民游走区 |
| 村民 | 4 位（阿茂/小渔/掌柜/阿晴），各有身份、上衣色、喜好、台词；`villagers.ts` 集中管理 |
| 对话打字 | 聊天 = 打出村民的英文短句（`Word.text` 为整句），复用打字引擎，完美 +10 / 普通 +6 |
| 好感 | 0~100 后台计算，每 20 点一颗心；每人每天限聊一次、送一次 |
| 送礼 | 投其所好 +15 / 普通 +5 / 反感 −3；喜好按物品 id 或前缀匹配 |
| 折扣 | 掌柜好感 ≥3 心 → 种子 9 折（`shopDiscount` 接进 `seedPrice`） |
| 迁移 | `normalizeState` 给旧档补 `villagers` 与 chats/gifts 统计 |

**送礼反应的关键取舍（用户反馈后改版）**：
- **不显示数值增减**（去掉 +15/−3、去掉「好感 +X」toast），也**不预告每件物品的喜恶**。
- 好感只用心形粗略表示，后台计算。
- 送出去后村民**说一句反应台词**（`reactions.like/neutral/dislike`），玩家靠语气判断送得对不对。喜好要自己摸索。
- 理由：数值直给会把「送礼」退化成查表；用对话传达态度才有社交味，也契合「对话 = 打字」的小镇主题。

**地图调整**：原 y8 的四块岩石让位给进镇道路，移到镇西石堆（x30-31）；杂草生成排除小镇（`inTownArea`）。

## v2.8 羊 + 土地扩建（已实现）

按路线做「更多动物 → 土地扩建」。繁殖暂缓，理由见末尾。

### 羊与剪毛

羊的产出逻辑**刻意和鸡牛不同**，否则只是换个贴图：

| | 鸡 / 牛 | 羊 |
| --- | --- | --- |
| 产出 | 每天喂 → 次日有 1 个 | 喂食累积羊毛，约 3 天攒满 |
| 收获 | 捡蛋 / 挤奶（三连词） | 剪毛（三连词） |
| 单价 | 蛋 70 / 奶 160 | 羊毛 280 |
| 定位 | 稳定日收入 | 耐心换高单价 |

- `Animal.wool` 0~100，`settleAnimalsOvernight` 里喂了 +34
- `isProductReady(a)` 统一判断：羊看 wool，其余看 productReady
- 羊的**身体随羊毛变蓬松**（渲染时半径随 wool 变化），一眼看出该不该剪
- 新买的羊 wool=100，带一份「见面礼」
- 羊住牛棚（复用 cow 围栏，`penBounds` 内部映射），符合原作牛羊同棚

### 动物命名

`Animal.name?`，买时默认「鸡1 / 羊2」，面板里「改名」按钮弹输入框。名字显示在面板标题和打字提示（`剪毛 · 棉花`）。

### 土地扩建

`FARM` 从单个矩形改成**区域数组** `FARM_AREAS`：

| 区域 | 范围 | 地块 | 解锁 |
| --- | --- | --- | --- |
| 0 | x11-16, y9-12 | 24 | 初始 |
| 1 | x17-19, y9-12 | 12 | 2500G |

- `PLOT_COUNT` = 36，`plots` 数组**始终是 36 个**，用 `state.farmUnlocked`（1 或 2）控制哪些可用
- `plotIndexOf` / `plotTileOf` / `plotAreaOf` 支持跨区域索引
- 未解锁区域：地形是草地、渲染跳过、交互提示「这块地还没开垦」
- 买地时 `unlockArea(k)` 铺泥土 + `applySeason` 重绘底图
- 读档后 `restoreUnlockedAreas()` 重铺（地形是运行时生成的，不存盘）
- 杂草不在任何耕地位置生成（含未解锁区），避免买地时地里一堆草
- 原 `[18,10]` 的树让位给新耕地，移到 `[21,12]`

### 存档迁移

旧档（24 个 plots、无 `farmUnlocked`、动物无 `wool`）：
- plots 补齐到 36，`farmUnlocked` 设为 1
- 动物 `wool` 补 0（羊补 100）
- `loadSave` 的长度判断从 `=== PLOT_COUNT` 放宽为 `> 0`

### 为什么这次没做繁殖

繁殖牵扯幼崽成长、性别/配种、上限与近亲，做浅了会变成「过夜随机多一只」的廉价奖励，不如留到有足够内容支撑时做整。已写进后续路线。

## v2.9 动物繁殖（已实现）

上面 v2.8 留的坑，这轮补上。

### 成长链

```
两只同类成年（心情≥70、当天都喂过）
  → 配种（打一个词）
  → 母方怀孕 2~3 天
  → 生一只幼崽
  → 幼崽养 4 天成年
  → 成年后才产出
```

| 动物 | 怀孕天数 |
| --- | --- |
| 鸡 | 2 |
| 牛 / 羊 | 3 |

### 设计取舍

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 幼崽能否产出 | **不能**（`isProductReady` 返回 false，羊也不涨毛） | 养大前只有投入没有回报，成长才有分量 |
| 谁怀孕 | 只有玩家点的那只 | 避免一次配种双倍产出 |
| 配种后 | 消耗**双方**的当日喂食 | 防止同一天反复配种刷数量 |
| 性别 | 不做 | 两只同类即可，降低理解成本；繁殖的价值在成长链不在配对 |
| 上限 | 每种 6 只（含幼崽） | 满了不生，避免无限膨胀 |
| 幼崽长大 | 送一份产出 | 让「养大了」立刻有反馈 |
| 近亲 | 不做 | 没有血缘数据，做了反而不透明 |

### 视觉反馈

- 幼崽整体 **scale 0.62**，头顶标「幼」
- 怀孕的头顶飘 **♥**（带呼吸缩放）
- 面板加「状态」行：`幼崽 · 还要 3 天长大` / `怀孕中 · 还要 2 天`
- 配种按钮只在成年且未怀孕时出现；条件不满足时置灰并说明缺什么

### 数据与迁移

`Animal` 新增 `adult: boolean`、`growDays: number`、`pregnantDays: number`。旧档缺这三项时 `normalizeState` 补 `adult=true, growDays=0, pregnantDays=0`（老动物都算成年）。

### 实现要点

- `settleAnimalsOvernight` 里四种结算顺序：产出 → 心情 → 幼崽成长 → 怀孕倒计时
- 生崽时新生儿先收进 `newborns` 数组，循环外统一 push，**避免在遍历中改数组**
- 上限判断要算上本轮已出生的：`countOfKind(state, kind) + newborns.filter(...)`

## v3.0 工具耐久（已实现）

给「工具」这条线补上消耗感——升级了却永不磨损，工具就只是永久增益。

| 等级 | 耐久上限 | 每次磨损 | 修满 |
| --- | --- | --- | --- |
| 铜 | 100 | 1 | 60G |
| 银 | 140 | 1 | 120G |
| 金 | 180 | 1 | 180G |
| 秘银 | 240 | 0.5 | 240G |

### 关键决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 修理收不收材料 | **只收金币** | 若收石材，会出现「修工具要石材 → 石材要镐挖 → 镐也坏了」的死锁。耐久系统最忌讳不可恢复状态 |
| 何时扣耐久 | 动作**成功完成**时（`spend`） | 超时失败活没干成，不该再扣耐久，避免双重惩罚 |
| 哪些动作扣 | 只有 `p.tool` 非空的 | 徒手的播种、收获不磨损，逻辑上也说得通 |
| 升级时 | **修满到新等级上限** | 升级=换了把新工具，顺带解决「升级后马上坏」的尴尬 |
| 磨损量 | 秘银 0.5，其余 1 | 升级既是效率提升也是耐久收益，强化「值得升」 |
| 阈值 | 20% 预警 | 低于 20% 提示一次「快磨坏了」，坏了再提示一次 |

### 节奏

铜级 100 耐久 ≈ 3~4 天农活，一周修一次。目标是让修理变成像浇水一样的例行小事，而不是频繁打断。

### 反馈层

1. **快捷栏耐久条**：每把工具下方一条 3px 细条，绿 → 橙（<20%）→ 红（0）
2. **商店行内文本**：`耐久 85/100`，颜色随比例变化；损坏显示「已损坏」
3. **修理按钮**：有磨损才出现，标价 `修 60G`；金币不够时置灰
4. **Toast**：跨过 20% 时「快磨坏了」；归零时「坏了！得修一修才能继续用」
5. **拦截**：耐久 0 时 `startAction` 直接拦下并提示，不进打字会话

### 迁移

`ToolState.durability` 是新增字段。旧档缺它时 `normalizeState` 按**当前等级**补满（比如金锄头补 180，而不是统一的 100）。

## v3.1 美术技法升级（已实现）

用户反馈「画面素材比较简陋」。先做了量化诊断，再决定路线。

### 诊断（改之前）

`render.ts` 1219 行里：

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| `fillRect` | 173 | 以矩形拼贴为主 |
| `strokeStyle` | 9 | **几乎没有描边** → 物体糊在一起 |
| 渐变 / 图案 | 0 / 0 | 纯平涂，无质感 |
| 硬编码颜色 | 132 | 无统一调色板，色彩关系乱 |
| `drawImage` | 1 | 无精灵，全靠几何图形 |
| `Math.sin` | 23 | 动画只有位移，无逐帧 |

**结论**：简陋主要不是「没素材」，而是「没做美术基本技法」。这部分不换素材也能修。

### 路线选择

| 路线 | 成本 | 上限 | 结论 |
| --- | --- | --- | --- |
| A. 技法升级 | 中（纯代码） | 中高 | **先做**，并由此判断值不值得投 C |
| B. 像素矩阵精灵 | 高 | 高 | 后续按需 |
| C. 外部 PNG 素材 | 最高 | 最高 | 上 Steam 时再评估 |

选 A 的理由：做好描边/调色板/光影后，如果还是「不够好看」，问题在美术功底而非技术，那时买素材也未必解决。**先排除技术变量**。

### 做了什么

新建 `src/palette.ts`，把颜色从散落硬编码收成规则：

1. **每材质 5 阶**：`hi / base / mid / dark / line`
2. **描边不用纯黑**：用材质最深一阶（偏暖）
3. **阴影色相偏移**：往蓝紫偏，不硬降亮度（避免发灰）
4. **统一左上光源**：高光在左上，阴影在右下
5. **柔和落地影**：`softShadow` 三层递减，替代单层纯黑

地形重做：
- 草地：9 簇「暗底 + 亮顶」草叶 + 起伏点
- 路面：碎石颗粒 + 砖缝暗线
- 水：底纹 + 双层波纹高光 + 岸沿
- 耕地：田埂描边 + 垄沟（暗槽 + 上沿高光）+ 土粒

建筑重做：
- 屋顶：**瓦片**（横排阴影线 + 每排高光 + 错位竖缝）+ 屋脊高光 + 屋檐
- 墙：木纹横板 + 顶部受光 + 木构架描边
- 窗：玻璃上下双色 + 斜向反光条 + 窗棂 + 窗台
- 门：木纹 + 门把高光

角色重做：
- 头部/身体/帽子走 `part()` 统一描边 + 顶部高光
- 草帽三层（描边 / 本体 / 高光）+ 缎带双色
- 眼睛带高光点，**周期性眨眼**
- 站立时**呼吸浮动**（0.5px 正弦）

作物重做：`fruitBall()` / `leafBlob()` 统一「描边 + 本体 + 左上高光」，南瓜加瓜棱、玉米加须。

动物重做：鸡/牛/羊都加描边与受光；羊的羊毛按 `wool` 变蓬松时保持描边一致；阴影换 `softShadow`。

村民重做：同样的描边/高光体系，名牌改成浅底深字（比原来的深底浅字更清晰）。

### 四季兼容

色板扩展为 4 阶草色（`grass / grassHi / grassDark / grassLine`），换季整体替换，所有草/树/花自动跟着变——**不需要为每个季节准备素材**。

### 验证

- 量化颜色数（8 级量化，全屏）：改前 498 → 改后 1214
- 采样确认各材质分了正确的阶：
  - 草地 3 色（base/hi/dark）
  - 屋顶 4 色（瓦片层次）
  - 耕土 4 色（含垄沟）
  - 水面多色波纹
- 功能回归：开垦、收获、耐久扣减均正常
- 控制台无报错

### 明确的上限

这条路的上限是「精致的程序化像素画」，不是手绘美术。要更进一步，得走 B（像素矩阵）或 C（PNG 素材）。两者可以和现状混用：**地形继续程序化，角色/动物/建筑换成精灵**。

## v3.2 场景系统：室内（已实现）

用户问「目前是没有进屋的设定的是吗」。确认：原来只是在门口弹一个面板（图鉴/睡觉/离开），人始终站在屋外。

### 三个体验缺口

1. 睡觉不用真进屋 —— 走到门边按空格就睡，缺了「回家」这段
2. 屋内视觉上不存在 —— 最重要的地方（家）只有一个门贴图
3. 功能位置别扭 —— 图鉴放在卧室弹窗里，它更像 UI 功能

### 架构：地图尺寸不变，室内只换地图形状

这是关键的降本决策。原本担心「多地图」要重构 `MAP_W/MAP_H`、相机 clamp、渲染尺寸，牵动面太大。实际做法：

- **地图仍是 50×22**，室内场景把整张图填成 `WALL_IN`，再挖出房间地板
- `buildScene(id)` 重填 `terrain`，`applySeason()` 重绘底图
- 相机、渲染、碰撞代码**一行没改**

新增 `T.FLOOR` / `T.FLOOR_STONE` / `T.WALL_IN` 三种室内地形。

### 家具用对象而非 tile

尝试过用 tile 拼家具，但 2×2 的床会被画成 4 个独立小块。改为 `FURNITURE` 数组（每个家具一次画完整）：

```ts
{ kind: 'bed', tx: 18, ty: 7, w: 2, h: 3, scene: 'house' }
```

碰撞由 `furnitureAt()` 判断（地毯 `rug` 可走），交互也走它（床→睡觉、书架→图鉴）。

### 室内动物

「进动物房」如果里面空的就没意义。做法：

- 动物没有场景归属，**同时存在于室内外**（玩家不会同时在两处看，不违和）
- 室内位置由 `indoorAnimalPos(scene, index)` 按序号排布，不游走
- `animalNearInScene()` 按场景选择用自由坐标还是排布坐标
- 住宅里没有动物，直接返回 null

### 场景切换

| 从 | 到 | 出生点 |
| --- | --- | --- |
| 农场门 (5,6) | 住宅 | (24,15) 面朝上 |
| 农场门 (4,15) | 鸡舍 | (23,15) |
| 农场门 (12,15) | 牛棚 | (24,16) |
| 室内门 | 农场 | 门外一格，面朝下 |

- 回农场时会**重铺已解锁耕地 + 恢复动态阻挡**（树/岩石），因为 `buildScene` 会清空
- 杂草生成加了场景守卫，室内不撒草
- 室内不画季节色罩与雨雪（但保留昼夜）

### 睡觉改动

从「门口弹窗」改成**必须走到床边**：床 → 确认框 → 睡觉。图鉴移到书架。

### 验证

| 项目 | 结果 |
| --- | --- |
| 进出三个建筑 | 六次进出场景与出生点全对 ✓ |
| 室内渲染 | 木地板 / 石地板 / 暗墙 / 床（枕头被子）/ 书架（书脊）/ 桌子 / 门 ✓ |

场景系统一旦有了，以后加**矿洞、酒馆、村民家**都只是「多一个场景 + 室内布局」，不用再动架构。

## v3.3 全局难度（已实现）

用户反馈「有些打字新手一下子玩不起来」。这个判断是对的——原来的默认参数对新手确实不友好：

- 铜工具容错 **0**，打错即断连击
- 超时只退**一半**体力
- `strawberry` 要打 10 个字符

### 三个难点，逐一拆开

新手卡住的不是单一因素，所以三档难度同时调四个维度：

| 维度 | 轻松 | 标准 | 挑战 |
| --- | --- | --- | --- |
| 时限倍率 | **1.7** | 1.0 | 0.85 |
| 容错加成 | **+2** | 0 | -1 |
| 词长档位偏移 | **-1** | 0 | +1 |
| 超时惩罚比例 | **0.25** | 0.5 | 1.0 |
| 打错是否清连击 | **否** | 是 | 是 |

实测同一词 `harvest`：轻松 6511ms / 标准 3830ms / 挑战 3256ms。

### 关键决策

**1. 难度不影响收益。**
这是刻意的——如果轻松档收益打折，新手会被"惩罚"；如果挑战档收益加成，又变成"想赚钱必须玩难"。两种都在制造压力。收益与难度解耦，难度只解决「能不能玩得动」。

**2. 轻松档「打错不清连击」是关键的一条。**
连击关系到体力回复（5/10/20/40 各回 2 点）。新手必然打错，如果每次打错都清连击，等于永远拿不到连击奖励，体验会非常挫败。这条比单纯加时限更能救新手。

**3. 中文提示始终显示，并且显示词义。**（曾被用户纠正）

最初的设计是「挑战档隐藏中文提示」——想用信息剥夺来制造挑战感。**这个想法被用户否掉了，而且否得对**：

- 你打的还是英文，隐藏提示只是让你**不知道自己打的是什么**
- 这是**信息剥夺**，不是技能挑战
- 它恰好砍掉了游戏最有价值的部分：打 `harvest` 顺带记住"收获"

顺着这条反馈又发现一个**更严重的问题**：中文提示原本显示的是**动作名**而不是词义。比如开垦时随机到 `sown`，提示写的是「开垦」，但 `sown` 是"已播种"；钓鱼时随机到 `bait`，提示写的是「抛竿」，实际是"鱼饵"。**这不但学不到词，反而会记错。**

修复：
- 给全部 **203 个内置词**补了中文释义（`WORD_ZH` 映射）
- 打字面板的中文行改为显示**词义**，动作名保留在上一行（「开垦 · 铜锄头」）
- 移除难度里的 `showZhHint` 字段

**4. 标题页选 + 顶栏随时改。**
新手可能玩到一半才发现打不动，必须能中途下调。顶栏难度徽章点开就能切，立刻生效（下次打字开始算）。

### 实现

新增 `difficulty.ts`，把 `applyDifficulty()` 与 `shiftBand()` 做成纯函数，6 个 `session.start` 调用点和 12 处取词全部走它们。

注意点：
- 容错做 `Math.max(0, ...)`，挑战档的 -1 不会把容错压成负数
- 时限做 `Math.max(0.3, ...)`，避免叠乘后过小
- `chosenDifficulty` 单独存一份：`newState()` 会把难度重置成 normal，标题页的选择必须记在外面

### 验证

| 项目 | 结果 |
| --- | --- |
| 三档时限 | 6511 / 3830 / 3256 ms ✓ |
| 三档容错 | 2 / 0 / 0（clamp 生效）✓ |
| 三档词长 | band2 → 1/2/3（4/5/6 字母词）✓ |
| 超时惩罚 | 0.25 / 0.5 / 1.0 ✓ |
| 轻松档打错 | 连击保留（5→5）✓ |
| 中文提示 | 始终显示，且显示词义：`husk`→谷壳、`bait`→鱼饵、`sown`→已播种 ✓ |
| 释义覆盖率 | 203 个内置词 / 203 条释义，零遗漏 ✓ |
| 标题页选择 | 三卡片渲染，选择写入 state ✓ |
| 游戏内切换 | 顶栏徽章 → 面板 → 切换生效 ✓ |

## 0. 现状诊断

当前版本里，"工具"其实不存在，只有一个全局数字：

```ts
state.tool: number  // 0 铜 / 1 银 / 2 金 / 3 秘银
```

它同时作用于开垦和浇水，本质是一把万能升级品。同理，"物品"也不存在：

- 种子 = 一张 `{ turnip: 6, potato: 0 }` 的计数表
- 作物 = 收获后直接进 `basket` 这个隐形数组，走到出货箱一键清空
- 动作 = 面朝地块按空格，系统自动判断是开垦 / 播种 / 浇水，玩家没有任何选择权

**结论**：工具体系要成立，必须先有"物品"这个实体；工具必须先成为可持有、可切换、可损耗、可升级的**东西**，然后才谈得上体系。

---

## 1. 设计原则

1. **工具改变的是打字的手感，不只是数值。**
   如果银锄头只是"体力 -10%"，那它只是一行配置表，玩家不会记得自己换了工具。
2. **背包是仓库，快捷栏是手边。**
   两者必须分离。收拾东西在背包，干活在快捷栏，不能每做一件事都开背包翻找。
3. **摩擦必须有出口。**
   任何"你拿错工具了"的时刻，都要用自动切换或明确提示化解，而不是让玩家茫然地按空格。
4. **新增的复杂度必须换回可见收益。**
   加了材料系统，就必须有新的动作（砍树、挖石、割草）和新的东西可做，不能只是多一层币。

---

## 2. 物品模型

```ts
type ItemKind = 'seed' | 'crop' | 'material' | 'tool' | 'consumable';

interface ItemStack {
  id: string;          // 'seed.turnip' | 'crop.tomato' | 'mat.wood' | 'tool.axe'
  kind: ItemKind;
  qty: number;
  quality?: number;    // 仅 crop，1~5
}
```

### 堆叠规则

| 类别 | 上限 | 说明 |
| --- | --- | --- |
| 种子 | 99 | 按作物种类堆叠 |
| 作物 | 99 | **按「作物 + 品质」分堆**，5 星萝卜和 1 星萝卜不混 |
| 材料 | 99 | 木材 / 石材 / 纤维 |
| 工具 | 1 | 每格一把，不可堆叠 |

作物按品质分堆会让同类作物最多占 5 格，这是一笔刻意的成本：**品质有价值，就得占地方**。

## 4. 快捷栏

8 格常驻屏幕右下，可用 `1` ~ `8` 直接选择，`Q` 循环。

- 工具放进去就是"手持"
- 种子放进去就是"手持种子"

**这是本次改动对操作的最大影响**：原来的 `1~7` 选种子会被快捷栏取代，种子要先从背包放进快捷栏。

初始快捷栏：`锄头` `水壶` `(空)` `(空)` `(空)` `(空)` `(空)` `(空)`。

### 自动切换规则

按空格时：

1. 手持物适用 → 直接执行
2. 不适用，但快捷栏里有适用的工具 → **自动切换并提示**「换成 锄头」
3. 不适用，且没有该工具 → 提示「需要锄头」并给出获取途径（订购箱）

自动切换可以在设置里关闭，给硬核玩家。默认开启，因为这是打字游戏，不是工具管理游戏。

| 钓竿 | 咬钩窗口从 1.2 秒放宽到 2 秒 |

### 升级配方

| 升级 | 金币 | 材料 |
| --- | --- | --- |
| 银 | 600 | 木材 ×8（斧/镐额外要石材 ×10） |

## 6. 打字模式：六种手感

这是"工具体系"真正的价值所在。每把工具的打字节奏都不同：

| 工具 | 模式 | 具体规则 |
| --- | --- | --- |
| 锄头 | 单次 | 一个词，标准判定 |
| 水壶 | 单次 | 一个词，成功后水流拖尾动画 |
| 斧头 | **三连击** | 同一个词连打 3 次；每命中一次树皮裂痕加深一级 |
| 镐 | **重击** | 一个长词；时限 -20%，容错为 0；命中时屏幕震动、碎石四溅 |
| 镰刀 | **快打串** | 3 个 2~3 字母短词连续打，每个只有 2.5 秒 |
| 钓竿 | **反应** | 抛竿（打 `cast`）→ 等待咬钩（随机 1~4 秒）→ 咬钩后 1.2 秒内按空格 → 再打 `reel` |

钓竿是唯一一个"等待 + 瞬间反应"的节奏，和农活的持续输入形成对比，适合放在碎片时间。

有工具就必须有靶子，否则斧头镐头无处可用。

| --- | --- | --- | --- | --- |
| 树 | 地图固定 12 棵 | 3 击 | 木材 2~4 | 砍倒后 3 天（树桩 → 小树 → 成树） |

## v3.4 词库：四级词汇 + 自定义释义（已实现）

用户要求「自定义词库支持 `词 释义`，默认用四级词汇」。

### 顺手发现的问题

上一轮把中文提示改成显示**词义**后，暴露出一个事实：内置农场词只有 203 个，每档 5~10 个，玩两天就开始重复。而用户要的是"能背单词"。

### 三层词库与优先级

| 词库 | 词数 | 默认 |
| --- | --- | --- |
| 自定义（用户导入） | — | 优先级最高 |
| 📘 四级词汇 | **2945** | **启用** |
| 🌾 农场主题词（6 分类） | 203 | 启用（被四级词覆盖） |

取词顺序：**自定义 > 四级词汇 > 农场主题词**。

设计上用"四级词汇启用时覆盖所有分类"，而不是"把四级词按 farm/chop 分类"——四级词本来就不分农场主题，硬分只会别扭。想保留主题趣味可以一键停用四级词。

### 关于"954 而不是 4500"

四级大纲约 **4500 词**，但其中大量是派生词（`abandon` → `abandonment` → `abandoned`），打起来手感几乎一样，放进游戏只会让每档膨胀、重复率反而升高。

最终收录 **2945 词**：中学基础词约 450 个 + 大学新增词约 2500 个。按难度分档：入门 124 / 轻松 290 / 中等 463 / 进阶 619 / 困难 527 / 高手 571 / 极限 351。

这个量级够玩 60 天以上不重复（洗牌袋保证一轮内不重复）。要更全的词表，走自定义导入。

### 自定义词库的释义格式

`CustomSet.words` 从 `string[]` 改为 `WordEntry[]`（`{en, zh}`）。

解析 `normalizeEntries()` 支持：
- `abandon 放弃`（空格）
- `abandon,放弃`（逗号）
- `apple 苹果; banana 香蕉`（分号分条）
- `abandon absorb abstract`（纯列表，无释义）

判据：如果"词后面的内容"里还含英文单词，就当作纯单词列表；否则当作释义。

**旧存档兼容**：`typing-farm-wordsets-v1` → `v2`，`toEntries()` 会把字符串数组转成 `{en, zh: ''}`。

### 教训

第一版只写了 **332 词**就标成"四级词汇"，被用户指出「四级不是有三四千吗」——名不副实。之后 954 → 2494 → **2945**（补上中学基础词），一共挤了四次。

两点教训：
1. **给功能起名时要对得上它的实际内容**，否则比不做更糟
2. 数量类承诺要一次给足——分四次挤出来的过程对用户是纯损耗

## v3.5 学习机制：让人真的记住单词（已实现）

用户提出：「主要目的还是让人能记住单词，所以也不是一下释放所有的词汇。」

### 先承认原设计是反学习的

原来的取词用**洗牌袋**：保证一轮内不重复 + 最近 8 词避让。这在玩法上是为了避免无聊，但与记忆规律直接冲突：

> 你今天打了 `abandon`，一周后才再遇到——那时早忘了。

**记不住词，正是因为不重复。** 而且 2945 词一次性全开放，等于把整本词典扔给人，没有课程表。

### 用户的第二个关键纠正

我提议用「打对 3 次算掌握」，用户否掉：

> 「这个实际上，打对就算掌握不行的，因为时照着打的。」

这句话是整个功能的转折点。面板上写着 `abandon`，玩家只是**把眼睛看到的东西复制到手上**——这是抄写，不是回忆。抄一百遍也记不住，因为大脑从没被要求「从中文想起英文」。

### 最终设计：两条同时成立才算掌握

**条件一：必须回忆（挖空）**

| 状态 | 显示 | 含义 |
| --- | --- | --- |
| 从没遇过 | `abandon` | 学习阶段，允许看 |
| 遇过但没掌握 | `a______` | **回忆测试**，只留首字母 |
| 已掌握 | `abandon` | 复习不该再卡你 |

已输入的部分照常显示，所以玩家知道自己打对没有，但仍须先想起来。

**条件二：必须跨天**

- 记录「在几个不同天打对过」
- **同一天重复打对只算 1 次**
- 满 3 个不同天 = 掌握

这一条堵死了「一天连打 20 遍刷满」——那种熟练度是假的。

**每日新词配额 12**

配额用完后只从已学词里取。睡一觉重置。

**取词优先级**（替换洗牌袋）

学过未掌握（高）→ 未见过的（受配额）→ 已掌握（低）。刚出现过的 12 个词排除，保证间隔但不「一轮内绝不重复」。

### 实现要点

- `learning.ts` 独立管理进度，存储键 `typing-farm-learning-v1`
- `Word.mask` 控制挖空起点（0 = 不挖）
- `makeWord()` 里**先算 mask 再 markSeen**——否则首次遇到就被挖空（这个 bug 犯过一次）
- `startLearnDay(day)` 在 `startGame` 和每日 `state.day++` 后调用，重置配额
- 词库界面显示「已学 / 已掌握 / 今日新词」

### 验证

| 项目 | 结果 |
| --- | --- |
| 首次遇到 | mask=0，完整显示 ✓ |
| 再次遇到 | mask=1，挖空 ✓ |
| 连续取词间隔 | 10 次取词 10 个不同词 ✓ |
| 每日配额 | 12 个新词后转为复习（`essay`/`stuff`/`mere` 全变 m1）✓ |
| 打对计数 | `days=1, lastDay=当前天` ✓ |
| 跨天重置 | 睡觉后 `learnDay` 1→2，配额归零 ✓ |
| 掌握判定 | days=3 时计入「已掌握」✓ |

### 一个测试陷阱

Vite dev 下用 `import('/src/learning.ts')` 拿到的模块实例与游戏内部**不是同一个**（HMR 导致双实例），导致我一度以为「所有取词都返回同一个词」。改用**真实游戏流程**（按键开垦 + 读面板/存档）才复现出正确行为。教训：涉及模块内部状态的验证，必须走游戏自己的调用路径。

### 后续修正：挖空被移除（v3.5.1）

上线前用户否掉了挖空：

> 「不要进行挖空，还是直接显示单词原文就行了，挖空就脱离的打字这个范畴设定了，难度提升太大了。」

**这个反对是对的，而且理由比"难度太高"更根本**：本作是**打字游戏**，玩家的任务始终是「把看到的词打出来」。挖空把任务换成了「从中文想起英文再打出来」——那是拼写测试（Anki 那类），塞进打字游戏是**脱离设定**的偷换。

而且它有体验断裂：前 12 个词正常打，第 13 个突然变填空题，玩家的心智模型会被打断。

**保留的**：跨天掌握（3 个不同天）、每日新词配额（12）、复习优先的取词顺序。
**移除的**：`maskFor` 恒返回 0（保留函数作为未来可选「挑战模式」的挂点）、`Word.mask` 字段、挖空渲染与样式。

**代价与收益**：去掉挖空后，"照着打"也能累计掌握，掌握门槛确实变低了。但**跨天重复本身仍是有效的间隔重复**——同一批词在 3 个不同天各打一遍，效果弱于主动回忆，但仍远好于"一周才见一次"。这是游戏作为游戏该付的代价。

### 教训（补充）

在"要不要挖空"这件事上，我一开始把**学习效率**放在了**游戏设定一致性**之上，方向就错了。用户的一句"脱离打字的范畴"点出了要害：
**功能可以有教育价值，但不能因此改变游戏类别。**

## v3.6 矿洞（已实现）

线二（经营内容）的第一项。场景系统在 v3.2 就已经做好，所以这次只是"多一个场景 + 一套室内布局"，成本很低。

### 设计：给工具升级补上资源链条

原来工具升级只要**木材 + 石材**——砍树挖石就够了，高级工具没有任何稀缺材料门槛。矿洞如果只是"又一个能挖石头的地方"，就没有存在意义。

所以把矿石接进升级配方：

| 升级 | 需要 |
| --- | --- |
| 铜 → 银 | 木材/石材（不变） |
| 银 → 金 | + **铜矿 4** |
| 金 → 秘银 | + **铜矿 6 + 铁矿 4 + 宝石 2** |

这样矿洞成了**高级材料的唯一来源**，玩家必须下去。

### 结构

| 层 | 矿石 | 节点 |
| --- | --- | --- |
| 1~2 | 铜矿 | 4 |
| 3~4 | 铜矿 ×2 + 铁矿 ×3 | 5 |
| 5 | 铁矿 ×3 + 宝石 ×2 | 5 |

- 每层一个上行梯子、一个下行梯子；第 1 层的上行梯子直接回农场
- 矿脉 `regrow: 0` **不重生**，出洞再进才刷新——可以反复刷，但有跑路成本
- 节点 key 带层级前缀（`m3:oreIron:20,9`），出洞时按前缀清理，不影响农场节点

### 几个实现细节

- `MINE_ROOM` 描述房间范围与梯子位置，渲染与逻辑共用
- `mineOrePlan(floor)` 决定每层产出，改数值只改这一处
- 矿洞地形新增 3 种 tile：`MINE_WALL` / `MINE_FLOOR` / `LADDER`
- 矿石节点有发光脉动（`Math.sin` 驱动 alpha），在暗环境里更醒目

### 踩过的坑

**`resolveTarget` 的兜底分支**：原代码是

```ts
if (node.kind === 'tree') ...
if (node.kind === 'rock') ...
return base('cut', '割草', 'sickle');   // ← 其余全当杂草
```

新加的三种矿石节点全被当成杂草，要镰刀才能割，于是"走到矿脉前按空格没反应"。必须显式判断矿石类型。

| --- | --- |
| 进入矿洞 | scene=mine, floor=1, 落点 (19,8), 生成 4 个铜矿脉 ✓ |
| 挖矿 | "挖矿 · 铜镐"，打两次后获得 `mat.copper ×2` ✓ |
| 上下楼 | 1→2→3→4→5→4 全通 ✓ |
| 层间矿种 | 3 层 = 铜+铁；5 层 = 铁+宝石 ✓ |

收货测试一开始「按空格没反应」，排查半天发现是**帮助面板没关干净**——`tryInteract` 第一行就 `if (UI.isModalOpen()) return`。而我的关闭按钮匹配写成了 `/关闭|离开/`，实际按钮文字是「知道了」，所以没匹配到。

## v3.8 花卉系统（已实现）

线二第三项。

### 定位：社交筹码，不是经济作物

关键设计决策是**让它亏钱**：种子 70G，卖只值 45G。如果花也能赚钱，它就会变成"第 16 种作物"，失去独立定位。

花存在的意义是给社交系统补上**通用筹码**：

| 礼物 | 好感 |
| --- | --- |
| 普通礼物（中性） | 5 |
| 普通礼物（对方喜欢） | 15 |
| 花（中性用途） | **10** |
| 花（对方喜欢花） | **20** |

原来只有「投其所好」一条路，玩家得先猜每个村民喜欢什么。花是**不用猜的那条路**，代价是亏 25G 和 4 天时间。

阿晴本身角色设定就是「爱花的姑娘」，所以 `likes` 加了 `'flower.'` 前缀通配。送她花（20）比送她最爱的草莓（15）还高——这是有意为之：角色设定应该压过数值偏好。

### 实现：复用作物管线

花就是 `kind: 'flower'` 的作物，走同一套种植 / 浇水 / 收获 / 季节逻辑。区别只在三处：

1. **物品前缀**：`flower.tulip` 而不是 `crop.tulip`（`cropItemId()` 按 kind 判断）
2. **渲染**：新增 `shape: 'flower'` 分支——细直茎 + 两侧叶 + 五瓣围花心
3. **送礼加成**：`giftGain()` 里花额外 +5

其余（种子生成、图鉴、商店行、季节限定）全部由既有循环带出来，没有新增 UI 代码。

### 验证

| 项目 | 结果 |
| --- | --- |
| 商店 | 19 种种子（15 作物 + 4 花），花显示「4天开花 · 卖只值 45G，但送礼好感更高」✓ |
| 渲染 | 郁金香粉 299px / 百合白 260px / 雏菊黄 686px / 山茶红 389px ✓ |
| 收获 | `flower.tulip` 入包（前缀正确）✓ |
| 送礼 | 阿晴收花 20、其他村民 10、普通礼物 5 ✓ |
| 图鉴 | 28 条（19 作物花 + 6 工具 + 3 动物），花条目有专属底色 ✓ |

### 一点取舍

没做「采蜜」——花田吸引蜜蜂产蜜听起来有趣，但那会引入第三套产出循环（花 → 蜂箱 → 蜂蜜），而花现在的定位是"低成本社交道具"，再加一条经济链会让它变得暧昧：既能赚钱又能加好感，那"亏钱换好感"的设计意图就没了。

如果以后要做采蜜，更合适的是**独立的蜂箱建筑**，而不是从花本身延伸。

## v3.9 产物加工体系（已实现）

用户指出：「这个还有一个前置，就是产物加工体系吧。」

**这个观察是对的，而且是结构性的**。如果直接从「牛奶」跳到「料理」，配方只能堆原始食材：

```
牛奶 → 蛋糕        ← 一步到位，中间没有任何可玩环节
```

正确的分层应该是：

```
作物 / 动物产物 → [加工台] → 加工品（食材） → [灶台] → 料理
                        ↑ 本次            ↑ 后续
```

加工体系还有一个作用：**给动物产物第二条出路**。原来牛奶/羊毛只能直接卖，现在能变成更值钱的东西。

### 五条配方

| 加工品 | 原料 | 时间 | 售价 | 增值 |
| --- | --- | --- | --- | --- |
| 🧀 奶酪 | 牛奶 ×1 | 4h | 420 | +260 |
| 🧈 黄油 | 牛奶 ×2 | 5h | 780 | +460 |
| 🪡 毛线 | 羊毛 ×1 | 6h | 520 | +240 |
| 🍓 草莓酱 | 草莓 ×2 | 5h | 1900 | +620 |
| 🥫 番茄酱 | 番茄 ×2 | 3h | 880 | +340 |

增值率 46%~100%，且**必须花时间**。

### 三条设计原则

**1. 必须花时间，不是免费增值。**
加工消耗几小时游戏时间，会跨天。如果点击即得，加工台就退化成"把东西在背包里过一遍"。

**2. 一次只能做一样（单槽位）。**
避免玩家摆一排放着批量刷。想多做就得回来收、再放。

**3. 品质继承原料。**
5 星牛奶做出的就是 5 星奶酪。这让「把动物心情养好」的价值不只是蛋奶本身，也传导到加工品上。

### 时间处理：绝对分钟数

跨天是这里唯一的难点。做法是把「完成时刻」存成**绝对分钟数**：

```ts
absoluteMinutes(day, time) = day * 1440 + time
doneAt = absoluteMinutes(今天, 现在) + 配方分钟数
```

这样跨天不需要任何特殊判断——第 2 天 6:00 的绝对值（3240）自然大于第 1 天 20:00 开始 + 6 小时的 3000。存档里也只需要两个数字。

### 验证

| 项目 | 结果 |
| --- | --- |
| 面板 | 5 条配方，显示原料 / 时间 / 售价 / 增值，缺料显示「缺料」并禁用 ✓ |
| 开始加工 | 牛奶 4→3，job 记录 quality=4（继承），4 小时后完成 ✓ |
| 占用中 | 其他配方显示「占用中」且禁用 ✓ |
| 未完成 | 按钮栏只有「关闭」，没有「取出」 ✓ |
| 完成 | 状态变「✅ 已做好」，出现「取出」，取出得 `craft.cheese` 品质 4 ✓ |
| 跨天 | 20:00 开始 6h（doneAt 3000），当晚未完成；次日 6:00（绝对 3240）已完成 ✓ |

### 下一步

加工品现在只是「更值钱的卖出品」，它真正的用途是**烹饪的食材**。所以烹饪的配方可以基于加工品来设计——

比如「奶酪焗菜」（奶酪 + 作物）、「草莓酱面包」（草莓酱 + 面粉）。这样三层链条才闭合。

## v3.10 烹饪 / 料理（已实现）

线二最后一项，也是三层生产链的收口。

```
作物 / 动物产物 → [加工台] → 加工品 → [灶台] → 料理
```

### 核心区别：料理能吃

加工品只是"更值钱的卖出品"。料理如果也这样，它就只是第四层加工。

所以给了料理**第二个用途：吃掉回体力**。

| 料理 | 原料 | 售价 | 回体力 |
| --- | --- | --- | --- |
| 🍲 蔬菜汤 | 萝卜 + 洋葱 | 380 | 25 |
| 🍳 煎蛋 | 鸡蛋 ×2 | 210 | 20 |
| 🥣 土豆泥 | 土豆 ×2 | 440 | 25 |
| 🧀 奶酪焗土豆 | 奶酪 + 土豆 ×2 | 1070 | 40 |
| 🍝 番茄意面 | 番茄酱 + 玉米 | 1850 | 45 |
| 🍞 草莓酱吐司 | 草莓酱 + 鸡蛋 | 2950 | 35 |
| 🍱 丰收大餐 | 奶酪 + 南瓜 + 玉米 | 2300 | **60** |
| 🍜 奶油浓汤 | 黄油 + 牛奶 + 土豆 | 1630 | 50 |

这补上了原本缺失的一环：**以前体力只能靠睡觉和连击回复**，没有主动补充手段。现在白天干活累了可以回家吃一顿继续干，游戏循环更完整。

### 三档阶梯

- **家常**：原料就在手边（萝卜+洋葱、鸡蛋、土豆），回 20~25
- **像样的一餐**：必须用加工品（奶酪、番茄酱、草莓酱），回 35~45
- **大餐**：多种高级食材（奶酪+南瓜+玉米），回 50~60，售价 1600~2300

这样玩家能明显感知到「做饭水平」的成长，而不是一开始就能做满汉全席。

### 实现要点

- 烹饪**即时完成**（区别于加工的几小时）——吃个饭不该等半天
- 但消耗 **3 体力 + 20 分钟**，避免"做饭"变成零成本的体力转换器
- 料理品质继承原料平均，和加工台一致
- 灶台面板同时列出「背包里的料理」（可吃）和「菜谱」（可做），不用来回切界面
- 体力满时「吃」按钮禁用

### 验证

| 项目 | 结果 |
| --- | --- |
| 面板 | 3 分档 8 道菜，显示原料 / 售价 / 增值 / 回体力，缺料禁用 ✓ |
| 做菜 | 奶酪2→1 南瓜2→1 玉米2→1，得 `food.feast` 品质 5 ✓ |
| 吃 | 体力 40 → 100（+60，上限封顶）✓ |
| 渲染 | 灶台火光 111px / 铁锅 480px ✓ |
| 出货 | 丰收大餐 5 星 ×2 = 7130G ✓ |

### 线二收尾

| 项 | 状态 |
| --- | --- |
| 矿洞 | ✅ 5 层 / 3 矿石 / 接进升级 |
| 更多作物 | ✅ 8 → 15 种 |
| 花卉 | ✅ 4 种社交筹码 |
| 加工 | ✅ 5 配方 |
| 烹饪 | ✅ 8 道料理 |

三层链条完整闭合：**种/养 → 加工 → 烹饪 → 吃或卖**。

## v4.0 NPC 自主行动：他们有自己的日子（已实现）

用户设想「NPC 接入大模型做自主行动和对话」。我提出 **C+B 分两步**（先规则驱动的自主行动，再受控生成的对话），用户确认先做 C。

### 为什么先做 C 而不是直接上 LLM

三个约束：

1. **这是打字游戏，不是聊天室**——自由对话会把核心玩法改成聊天
2. **教育价值建立在可控词表上**——LLM 自由生成的词不在词库里，不计入掌握度，"背单词"就废了
3. **纯前端接不了 LLM**——暴露 API key 等于泄露，需要后端或 Electron 主进程代理

而「自主行动」这件事**根本不需要 LLM**：日程 + 状态机就够了。成本零、延迟零、不会出戏。

### 设计：日程表 + 朝目标走

```ts
interface ScheduleEntry {
  from: number;        // 起始分钟
  to: number;          // 结束分钟
  spot: Spot | ((season) => Spot);   // 目标地点（函数形式用于随季节变）
  onlyWeather?: Weather;   // 只在特定天气生效
  onlySeason?: Season;
  doing: string;           // "钓鱼"、"看店"——头顶显示
}
```

`resolveSchedule()` 按顺序取**第一条满足条件**的日程，所以「雨天」这类特殊条目写在前面。返回 null 表示这个时间不出门。

四个村民的日程：

| 村民 | 上午 | 中午 | 下午 | 傍晚 |
| --- | --- | --- | --- | --- |
| 阿茂 | 农田边看庄稼 | 广场吃饭 | 田里翻地 | 广场聊天 |
| 小渔 | 池塘钓鱼 | 池塘钓鱼 | 收竿 | 广场 |
| 掌柜 | 店门口 | 看店 | 看店 | 广场散步 |
| 阿晴 | 当季花田 | 广场聊天 | 广场 | 广场看日落 |

**联动**：雨天小渔避雨、阿晴躲屋檐；雪天阿晴躲雪；换季时阿晴的花田位置跟着变（`flowerSpot(season)`）；深夜全部回家（`active=false`，渲染与交互都跳过）。

### 没有做寻路，这是刻意的

移动只有：**朝目标点直线走 → 走不动就横向蹭一下**。

目标是让人显得**有生活**，不是显得**聪明**。真做 A* 寻路，代码量翻几倍，而玩家感知不到差别——他们只看到"阿茂在田边站着""小渔在岸边坐着"。

### 一个必要的取巧

村民从农田走到广场大约 55 秒。如果玩家看着，会看到"有人横穿整个镇子"，非常出戏。

所以：**换目的地时如果距离超过 11 格，直接到场**（视为"从别处赶来"）。近距离仍然走过去，所以玩家看得见的是自然走路。

配合 `spotKey` 记录当前目标，避免每帧重复传送。

### 头顶显示"在做什么"

名字牌下面加一行小字：「看庄稼」「钓鱼」「看店」「看花」。

这是"有生活"最直接的证据——**不用问也知道他现在忙什么**。

| 13:00 | 阿茂(39,10)吃午饭 / 阿晴(39,10)和人聊天 ✓ |

## v4.1 A* 寻路 + 点击移动（已实现）

用户提出两点：**寻路要做**，以及**加点击自动走动**——理由是「用 WASD 操控的时候有点影响打字」。

第二点的观察很准：这是个打字游戏，左手常驻 WASD 意味着每次打字都要把手移回键盘区。**移动不该占用打字的手。**

### 一份寻路，两处使用

新建 `pathfind.ts`：4 方向 A*，50×22 格，单次 < 2ms。

- **NPC**：沿路径绕过池塘、房屋、围栏走到日程目标点
- **玩家**：点击地面 → 算路径 → 沿路径走

之前 NPC 是「朝目标直线走 + 被挡就横向蹭」，遇到池塘会贴着边缘蹭很久。现在是真的绕过去。

**为什么 4 方向而不是 8 方向**：角色贴图只有上下左右四向，斜走会让朝向和位移对不上，看起来像在滑。

### 点击移动的几个细节

| 情况 | 处理 |
| --- | --- |
| 点到水面 / 墙 / 树 | `nearestWalkable()` 找最近的可行走格，走过去而不是没反应 |
| 移动中按移动键 | **立即打断自动移动** |
| 移动中开始打字 | 不打断（`updatePlayer` 在打字时暂停，打完继续走） |
| 到达 | 路径清空，站定 |
| 自动移动速度 | 150 px/s（略慢于手动的 168，让"自动"显得从容） |

点击位置会有一个蓝色小粒子作为反馈，让玩家看得见"要走到那去"。

### 验证

| 项目 | 结果 |
| --- | --- |
| 跨图寻路 | (10,10)→(40,10) 共 32 格，1.5ms，简化成 5 个拐点 ✓ |
| 绕池塘 | (18,16)→(28,16) 直线 10 格，实际 16 格，绕到 y=13 ✓ |
| 无障碍时 | (11,11)→(16,11) 恰好 5 格，不多绕 ✓ |
| 点水面 | 点池塘中心 (23,16) → 目标变成 (23,13)，走到水边 ✓ |
| 点击设路径 | 路径 5 段、终点 (30,11) ✓ |
| 沿路径移动 | 位置从 (8,9) 推进到 (12,9)，路径点在消费 ✓ |

### 一个测试环境的坑

DevTools 里 `requestAnimationFrame` 会被节流到 **1 帧/秒**，导致：
- 点击后玩家看起来"没动"（实际每帧走 150px，但一秒才一帧）
- 键盘打断自动移动测不出来（清空 path 的逻辑在 `updatePlayer` 里，不跑帧就不执行）

所以涉及逐帧逻辑的验证，在这个环境里只能用「路径是否被设置/消费」这类状态判断，不能靠观察位置。**真实浏览器里手感需要用户自己试。**
